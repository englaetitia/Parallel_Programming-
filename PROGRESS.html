Step 1 — Create our virtual machines (VMs)

Done started 20 Nov 2026
Why this step? MPI needs several computers that run the same system and the same MPI version. Laetitia's and Georges-Anthony's laptops are different (Windows, different settings). So each of us runs a small virtual machine: a "computer inside the computer" running Ubuntu Linux. All the VMs are identical, so MPI sees a clean, uniform cluster.

Who does what

Both of us do this step, each on our own laptop. Each VM gets a name: heat-laetitia and heat-georges. We also need a third machine (a lab PC, a family laptop…) because the final demo needs at least 3 VMs.

1. Install Multipass on the laptop (Windows) — from the terminal

Open PowerShell as Administrator (Start → type "PowerShell" → right-click → Run as administrator).

# a) Which Windows edition do I have? (Home or Pro decides the VM engine)
(Get-ComputerInfo).WindowsProductName

# b1) Windows PRO only: turn on Hyper-V, then restart the PC
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V -All

# b2) Windows HOME only: install VirtualBox (Multipass uses it as the engine)
winget install Oracle.VirtualBox

# c) Install Multipass (both editions)
winget install --id Canonical.Multipass -e --accept-source-agreements --accept-package-agreements

# d) Check it is installed
winget list multipass                                         # shows: Multipass  Canonical.Multipass  1.17.0
Test-Path "C:\Program Files\Multipass\bin\multipass.exe"     # shows: True

# e) If "multipass is not recognized": add it to PATH for this window
#    (restarting Windows fixes it permanently)
$env:Path += ";C:\Program Files\Multipass\bin"

# f) Final check
multipass version            # multipass 1.17.0+win / multipassd 1.17.0+win
multipass get local.driver   # hcs  (the new Windows engine in Multipass 1.17 — normal)

Simple words: winget is Windows' built-in app installer for the terminal. The driver is the engine that actually runs the VM; in Multipass 1.17 on Windows it is called hcs (it replaced the older hyperv driver).

2. Create the VM (in PowerShell)

multipass launch 24.04 --name heat-laetitia --cpus 2 --memory 4G --disk 15G
multipass list                     # should show heat-laetitia "Running"
multipass shell heat-laetitia      # opens a terminal INSIDE the VM

Georges-Anthony uses --name heat-georges. If your laptop has many cores and lots of RAM, you can give more (e.g. --cpus 4 --memory 8G).

3. Install the software (inside the VM)

sudo apt update
sudo apt install -y build-essential cmake git openmpi-bin libopenmpi-dev python3-numpy python3-matplotlib
mpirun --version      # write down the version: it must be the SAME on every VM
g++ --version

What these are: build-essential = the C++ compiler; cmake = build tool; openmpi = the MPI library and mpirun; numpy/matplotlib = for plots later.

4. Get our code inside the VM

cd ~
git clone https://github.com/englaetitia/Parallel_Programming-.git heat
cd heat && ls

Both VMs must keep the code at the same path (/home/ubuntu/heat), because MPI starts the program at the same place on every machine.

Step 2 — Connect the VMs with Tailscale

Done started 21 Nov 2026, 11:33
Why this step? Our two VMs live on two different laptops, maybe on different Wi-Fi networks, each hidden behind its own router. They can't see each other. Tailscale builds a private, encrypted network between them (our tailnet). Each VM gets a fixed address like 100.x.y.z and a name (heat-laetitia, heat-georges), and they can reach each other from anywhere. MPI will send all its messages through it.

Who does what

PartLaetitiaGeorges-Anthony
A. AccountCreates the Tailscale account (she owns the tailnet) and invites Georges-AnthonyAccepts the invite email
B. InstallEach installs Tailscale inside their own VM (at the same time)
C. Log inVM name heat-laetitiaVM name heat-georges
D. TestEach pings the other's VM and notes "direct" or "via DERP"

A. Account (Laetitia, in the Windows browser)

  1. Go to tailscale.com → Get started → sign in (Google, GitHub or Microsoft). The free plan is enough.
  2. Skip the "install on this device" screens. We install Tailscale in the VMs, not on Windows.
  3. Open the admin console (login.tailscale.com/admin) → Users → Invite users → Georges-Anthony's email.
  4. Georges-Anthony accepts the invitation email and signs in. He is now a member of our tailnet.

B. Install Tailscale (each of us, inside our own VM)

# on Windows, open the VM shell
multipass shell heat-laetitia          # Georges-Anthony: heat-georges

# inside the VM
curl -fsSL https://tailscale.com/install.sh | sh
tailscale version

C. Join the tailnet (each of us, inside our own VM)

sudo tailscale up --hostname=heat-laetitia     # Georges-Anthony: --hostname=heat-georges

It prints a link like https://login.tailscale.com/a/xxxxxxxx. Copy it into the Windows browser and sign in with the same account you used in part A. The terminal then says "Success."

tailscale status          # lists BOTH VMs once both have joined
tailscale ip -4           # our VM's 100.x.y.z address
ip addr show tailscale0   # the network card MPI will use (name must be "tailscale0")

D. Test the connection (each of us, towards the other)

# Laetitia's VM → Georges-Anthony's VM   (Georges-Anthony does the opposite: heat-laetitia)
ping -c 3 heat-georges
tailscale ping heat-georges

tailscale ping ends with either "via <IP:port>", meaning a direct connection (good), or "via DERP(xxx)", meaning traffic goes through a relay server (slower). Write it down: it explains our timings later.

If something goes wrong

  • No login link, but curl -4 works: turn off IPv6 and lower the MTU, then retry: sudo sysctl -w net.ipv6.conf.all.disable_ipv6=1, sudo ip link set dev eth0 mtu 1400, sudo systemctl restart tailscaled, sudo tailscale up --hostname=… --reset.
  • No login link, logs say "fetch control key … context deadline exceeded": the VM can't reach controlplane.tailscale.com. Test with curl (IPv4 vs IPv6), or switch network (phone hotspot).
  • "context canceled": you pressed Ctrl+C, which stops a command in Linux. Copy with mouse selection + right-click instead.
  • Install script fails or hangs: slow internet. Run the same curl … | sh line again.
  • Only one VM in tailscale status: the other person signed in with an account that isn't in our tailnet. Use the invited account.
  • ping by name fails but ping by 100.x IP works: MagicDNS is off. Admin console → DNS → enable MagicDNS.
  • Always "via DERP": the network (campus Wi-Fi often) blocks direct connections. It still works, just slower. Try a hotspot to compare.

Simple words

  • Tailnet: our private network, made of only our devices.
  • MagicDNS: lets us use names (heat-georges) instead of numbers (100.x.y.z).
  • DERP: Tailscale's relay servers, used when two devices can't connect directly. They work, but add delay (latency).
  • Latency: how long one message takes to arrive. This will be the key number for our performance study.

Step 3 — Passwordless SSH between the VMs

Done started 21 Nov 2026, 11:33
Why this step? When we run mpirun on one VM, it must start our program on the other VM too. It does this by logging in to the other VM with SSH (a secure remote terminal). It can't type a password, so each VM must be able to log in to the other without a password. We do this with an SSH key pair.

The idea, in simple words

  • Each VM creates a key pair: a private key (stays secret, never shared) and a public key (safe to share).
  • We give our public key to the other VM, which adds it to its list of trusted keys (~/.ssh/authorized_keys).
  • From then on, when our VM connects, the other VM checks the key and lets us in without a password.
  • Multipass VMs don't allow password logins, so the usual ssh-copy-id doesn't work. We copy the public key by hand (via WhatsApp or another chat).

1. Create a key pair (each of us, in our own VM)

ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub

The second command prints one line starting with ssh-ed25519 AAAA… and ending with ubuntu@heat-<name>. That's the public key. Copy the whole line (mouse + right-click) and send it to the other person. Never share ~/.ssh/id_ed25519 (without .pub): that's the private key.

2. Trust the other person's key, and our own (each of us)

# paste the OTHER person's line between the quotes
echo "ssh-ed25519 AAAA...their-key... ubuntu@heat-georges" >> ~/.ssh/authorized_keys

# also trust our own key (mpirun may log in to our own VM too)
cat ~/.ssh/id_ed25519.pub >> ~/.ssh/authorized_keys

chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

>> adds a line at the end of the file (a single > would erase the file, including the key Multipass put there). The chmod lines make the files private, because SSH refuses keys in files others could change.

3. Test (each of us, towards the other and towards ourselves)

ssh heat-georges hostname      # Georges-Anthony: ssh heat-laetitia hostname
ssh heat-laetitia hostname     # Georges-Anthony: ssh heat-georges hostname

The first time, SSH asks "Are you sure you want to continue connecting (yes/no)?". Type yes and press Enter. Then it should print the other VM's name (heat-georges) without asking for any password. Run it a second time: no question at all this time. That's the goal, because a pending question would make mpirun hang.

Checklist

  • Key pair created in heat-laetitia
  • Key pair created in heat-georges
  • Public keys exchanged and added to authorized_keys on both
  • ssh heat-georges hostname works from heat-laetitia, no password, no question
  • ssh heat-laetitia hostname works from heat-georges, no password, no question
  • Each VM can also ssh to itself

If something goes wrong

  • "Permission denied (publickey)": the other VM doesn't have your public key yet, or the line was pasted incompletely (it must be one single line). Check with cat ~/.ssh/authorized_keys on the other VM.
  • "Could not resolve hostname": Tailscale is down on one VM. Check with tailscale status.
  • Asks for a password: same as "Permission denied": the key isn't trusted yet.

Step 5 — Measure the network (ping-pong)

In progress started 21 Nov 2026, 11:50
Why this step? Later we must explain why our parallel program is fast or slow. That depends on two numbers about our network: latency (ts) is the fixed delay of any message, even a tiny one, and bandwidth (1/tw) is how many bytes per second flow once a message is moving. The model is t(m) = ts + m·tw (background notes, Section 8.4). We measure both, inside one VM and between the two VMs. These numbers are needed for checkpoint C1.

How the ping-pong works

  • Rank 0 sends a message of m bytes to rank 1, and rank 1 sends it straight back. That's one round trip.
  • Repeat 50 times (small messages), 10 (medium) or 3 (big), and average. One-way time = half the round trip.
  • Sizes: 8 B, 16 B, 32 B … up to 16 MB (powers of two, 22 sizes). One untimed "warm-up" exchange first for each size.
  • Small messages show the latency; big messages show the bandwidth.

tools/pingpong.cppThe measurement program. Exactly 2 processes. Prints a CSV table: bytes, reps, avg_round_trip_s, one_way_s, bandwidth_MB_per_s, plus a first line saying which VM each rank ran on.
